# NVDA 2026 MBROLA compatibility port

## Confirmed architecture mismatch

The installed `espeakWitMbrola` add-on's `espeak.dll` and `mbrola.dll` are both 32-bit (`i386`). NVDA 2026 runs its main process as 64-bit, so its existing `ctypes.LoadLibrary("espeak.dll")` fails with `WinError 193` before MBROLA initialization. Loading only one DLL as 64-bit would not solve the problem; both are loaded into the same process by the original driver.

## Prototype implemented

The compatibility prototype is under `addon/synthDrivers/`:

- `espeak_mbrola_host.cpp` — a small x86 helper that loads the existing DLLs and calls eSpeak's C API.
- `espeakMbrolaHost.exe` — the compiled x86 helper.
- `_espeak_mb.py` — an NVDA-side bridge module with the API expected by the installed `espeakwithmbrola.py` driver.
- `tools/smoke_mbrola_host.py` — a standalone test client for the helper.
- `tools/smoke_mbrola_bridge.py` — a targeted bridge check using a fake NVDA `WavePlayer`.

The host uses length-framed binary messages over pipes. Audio is streamed from eSpeak's synthesis callback; packets include PCM, the current sample rate, and marker offsets. The NVDA-side module filters stale generations, forwards PCM to `nvwave.WavePlayer`, recreates the player on a sample-rate change, and sends voice/parameter and speech-control commands to the helper.

Utterances are now synthesised in memory through `mbrola_stream.dll` (the
project's MBROLA sources built as a one-channel DLL) and forwarded in 20 ms
audio packets, so the first audio of an utterance arrives in a few milliseconds
and queued utterances join without a noticeable gap. The bridge tracks one
`_Feed` per utterance: cancelling aborts it, and audio that a blocked
`WavePlayer.feed()` call queues after the player was stopped is discarded, so an
interrupted utterance cannot resume midway. Index marks are announced when the
audio in front of them has played; marks eSpeak swallows at sentence boundaries
are announced just before the next reported mark. See `AGENTS.md` for the
measurements and for the `ESPEAK_MB_MBROLA_EXE=1` fallback that uses
`mbrola.exe` with bit-identical audio.

No generic RPyC `SynthDriverProxy32` is used. The host is a dedicated native child process following the low-overhead ProTalker approach.

## Build and smoke-check result

Build:

```powershell
g++ -m32 -std=c++17 -O2 -Wall -Wextra -Wno-cast-function-type `
  -o build\bin\espeakMbrolaHost.exe `
  addon/synthDrivers/espeak_mbrola_host.cpp
```

`objdump -f` reports `i386` for the resulting executable. A standalone run against the installed add-on selected `mb-en1` and synthesized 27,308 bytes of 16-bit mono PCM at 16 kHz. It returned marker indexes 42 and 43. Its one-off WAV was removed during project cleanup and can be regenerated by the smoke script.

The x64-side bridge check selected `mb-en1`, sent rate/volume/pitch/range parameters, and delivered the same 27,308 PCM bytes at 16 kHz to its fake `WavePlayer`, with event sequence `[42, 43, None]`; its WAV output is `output/test_mbrola_bridge_en1.wav`.

The marked smoke phrase produced both eSpeak mark events at 16 kHz. The user subsequently confirmed the installed port works in NVDA 2026: speech plays and cancels as expected. This completes the driver compatibility gate; custom database construction is the next project task.

## Port deployment

The tested deployment replaces the installed add-on's `_espeak_mb.py` with the project bridge and places `espeakMbrolaHost.exe` alongside the existing x86 DLLs and `espeak-data`. The original `espeakwithmbrola.py` driver remains unchanged.
